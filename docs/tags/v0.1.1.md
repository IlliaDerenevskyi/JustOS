v0.1.1 — Milestone 0 fix: the framebuffer and the boot code in one 2 MiB

A fix for Milestone 0 (`v0.1.0`). The public types, function names, and
result codes do not change.

- Fixed: AArch64 with UEFI did not start the kernel on a firmware that puts
  the framebuffer in the same 2 MiB as the boot application (found in CI with
  the Ubuntu firmware). The boot-time page tables made that whole 2 MiB block
  non-executable, and the processor faulted right after the MMU was switched
  on. Now a 2 MiB block (AArch64) or page (x86_64) that the framebuffer fills
  only in part is split into 4 KiB pages: the framebuffer pages are device
  memory without execute, the rest keeps its attributes. A block that the
  framebuffer fills completely stays one block. The same rule is now written
  for x86_64, where the problem could appear the same way.
- Specification (Rule 33): item (b) of `jp_x86_64_setup_paging` and
  `jp_aarch64_setup_paging` in `milestone0.md`, and a record in the Stage 1
  Implementation Acceptance. Code: `map_framebuffer_part` in
  `src/boot/architecture/{x86_64,aarch64}.c`. Tests: one new host test for
  each architecture.
- CI: jobs are split by architecture (host x86_64 and AArch64 with gcc and
  clang, QEMU x86_64 and AArch64); `CI/install_qemu_deps.sh` and
  `CI/qemu_tests.sh` are the scripts behind them. The host tests no longer
  depend on the address layout of the machine, and the freestanding kernels
  are linked without PIE.
- Checked: host tests (gcc and clang), QEMU tests on all three platforms
  (also with the Ubuntu AArch64 firmware), KVM tests, and a manual run of the
  four scenarios (normal, menu, recovery, panic) on x86_64 UEFI, x86_64 BIOS,
  and AArch64 UEFI in virt-manager.

Not included: the same as in `v0.1.0` (a run on a physical machine, saving
the configuration, choosing a kernel, an interactive recovery).
