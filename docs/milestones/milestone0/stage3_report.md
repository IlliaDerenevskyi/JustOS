## 2. How the code was checked

- Warnings are errors, gcc and clang; every Stage 3 source also compiles for the two kernel targets with `-DJP_BOOT_ONLY_<ARCH>`.
- **Mutation checks** (the new script skips changes inside comments). Survivors left are equivalent changes: loops that read one slot past the end, a spin-limit boundary, checks that another check already makes redundant, and failure paths of operations that cannot fail.
- The QEMU run found two things that the host tests could not: a large structure assignment (the whole report) made the compiler call `memcpy`, which the kernel does not have (fixed by copying field by field, and the rule is written in the specification); and the kernel at `-O2` in the upper half of the address space needs `-mcmodel=kernel` on x86_64.
- **The panic screen and the screen path in QEMU** (added after the first report): the variant `panic` (Stage 2 fails, the Stage 4 stand-in `fake_boot_manager_rejects.c` refuses the recovery transition, Stage 3 shows the panic screen and halts) is run by `tests/qemu/run_panic_test.py`. It waits for the last panic line on the serial port, asks QEMU for a screen dump (QMP `screendump`), and checks the eight panic lines and the Stage 3 text area pixel by pixel against the expected text (drawn with the independent font of the test kernel). All three platforms pass, also after the mutations "a glyph is drawn one pixel to the right" and "a panic line has a wrong label" (both fail the test).
- Rules self-check: tabs, `jp_` prefix, private helpers `static`, no `TODO`, no `malloc`, no mutable global data, no `memcpy`/`memset` in `src/boot` Stage 3 files.

## 3. Decisions taken beyond the text of the original specification (please review)

All are in `milestone0.md` ("3 Decided rules"). Items 1 to 5 were asked of the project owner; the rest are *derived* and listed so the reviewer can disagree.

1. The serial port: COM1 `0x3F8` (115200 8N1) and the PL011 at `0x09000000`, with a probe; an unavailable port is reported as such.
2. A built-in 8x16 font in `src/boot`, text lines without scrolling.
3. Event 0 of the log is a copy of facts about Stage 1; the attempt identity is a counter.
4. The Stage 3 stopping routine that Stage 4 mentions is `jp_boot_recovery_enter(NULL, JP_RECOVERY_TERMINAL_HALT)`.
5. New text is written for a junior reader; the older Stage 3 text is not rewritten yet.
6. *Derived:* Stage 3 runs inside the kernel and is called by Stage 4; it has no entry function of its own.
7. *Derived:* the contents of the `stage3` area and where its types live (`diagnostic_types.h`).
8. *Derived:* the status graph and which stage tag fits which status; a change to `FAILED` needs a recorded error.
9. *Derived:* the exact retention rule of a full log (an `ERROR` or `FATAL` event is never removed, even for a newer `FATAL` one); `boot_attempt_id` and `event_sequence` are always set by the log.
10. *Derived:* default severity (`FATAL` when not recoverable, otherwise `ERROR`); an override that would weaken a default makes the whole call fail.
11. *Derived:* the decision rules (`JP_BOOT_FAILED` from Stage 2 gives `ENTER_RECOVERY`, corrupted data gives `TERMINAL_HALT`; a retry never happens because the maximum is 0).
12. *Derived:* the panic screen text, the events of the panic, what `recovery_enter` does for each decision, and the retry with undo (it cannot run in Milestone 0; it is tested with a larger limit).
13. *Derived:* what makes a report consistent; `error` all zero means "no error".

## 4. Known limitations and gaps (for the reviewer's attention)

1. **Serial ports are fixed addresses.** On a machine whose UART is elsewhere, the diagnostics go to the screen only. The AArch64 address is the one of QEMU's `virt` machine.
2. ~~The screen path ran only on the host.~~ Closed: the QEMU `panic` test compares the real screen dump (section 2). The screen of real hardware is level M.
3. The retry (reset, history event, undo) is correct by unit tests but never runs in Milestone 0 (the maximum is 0).
4. **The stand-ins of Stage 4** (`fake_stage2_complete.c`, `fake_boot_manager.c`, `fake_stage3_lines.*`; the test tool `fake_boot_manager_rejects.c` stays) are on the list of fakes to replace after Stage 4.
5. ~~The panic screen was never shown in QEMU.~~ Closed: the variant `panic` (section 2). The processor halts after the panic, so this test is run by a Python observer instead of `run_test.sh`.
6. The older text of Stage 3 (about 2000 lines) was not rewritten for a junior reader.
7. Nothing was run on real hardware.
8. The Specification Lock Decision of Stage 3 was signed on 2026-11-21 (the owner's explicit instruction, after the points 2 and 5 were closed). The Implementation Acceptance was recorded on 2026-11-21 after the commit.
